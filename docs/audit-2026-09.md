# QA passes, September 2026 — findings and fixes

Five consecutive passes over the same branch, each asked for because the last
one had found enough to make the next worth doing. Recorded together because
the shape repeats and the shape is the transferable part.

**Every finding across all five was found by exercising something rather than
reading it, and every one looked unremarkable in the source.**

The method for passes 1–4, stated once: enumerate the rules from the catalogue —
`pg_policies`, `pg_constraint`, grants, storage policies — then attack each one
**and its neighbours**. Roughly half the findings were in a neighbour: the rule
itself was right, and something beside it walked around it.

Pass 5 changed instrument. Four passes of database and source review had said
nothing about what a person actually sees, so the fifth signed in as a patient
and as a clinician in a real browser and looked. Every finding it produced is in
the layer the first four could not reach, and none of them would have been found
by reading a policy.

---

## Pass 1 — review after the agreement work

Three findings, all in code written earlier in the same session.

### 1.1 A bypass beside the new mechanism — *severe*

`retract_health_document()` was the first cut of withdrawal and was still
granted to `authenticated`. Nothing in the client called it, but **PostgREST
exposes every granted function**, so the entire authority model shipped with a
door beside it: a document of any age withdrawn on free text instead of a reason
code, no second signature however old the disclosure, and no
`document_retraction_events` row — no evidence beyond a single audit line.

The lesson, stated the way it generalises: *adding a stricter path does not
remove a permissive one*, exactly as adding a restrictive RLS policy does not
narrow a permissive one. Both the function and the duplicate remnant view were
removed, and the surviving test now asserts the old function is **absent**
rather than merely unused.

### 1.2 A transaction-scoped flag left the door open behind it

`withdraw_shared_file()` announces itself to a guard trigger before it writes,
because `SECURITY DEFINER` changes the executing role but not the JWT claim — so
the function's own write is indistinguishable from a client's by actor.

`set_config(…, true)` is scoped to the **transaction**, not the statement.
Leaving the flag set disabled the guard for every later write in the same
request: one legitimate withdrawal holding the door open behind it. It is
cleared immediately after the write, and a test asserts the flag does not
outlive the call.

### 1.3 A guard that guarded nothing

The same commit added a trigger on `health_documents` with a comment claiming it
was load-bearing. It was not: RLS already refuses a row whose `retracted_at` is
being set, raising `42501`, and the trigger only converted that **loud refusal
into a silent no-op** — the wrong direction. Removed.

The equivalent on `messages` stays, because there it is real: the read-status
policy lets a recipient update the row and says nothing about the attachment
columns, so without it a patient could withdraw a clinician's attachment and
take a clinical instruction out of the thread with no record. Established by
dropping each trigger in a live database and watching which one changed the
outcome.

**The test covering this was wrong the same way for two rounds** — it asserted a
case RLS already handled, so it passed with the guard removed, which is exactly
the failure it was written to catch.

## Pass 2 — the Vault and its files

Three findings, all in the gap between a row and the bytes behind it.

### 2.1 The harness gap that hid the rest

Supabase grants `authenticated` select, insert, update and delete on
`storage.objects`; the local shim granted nothing. Every probe against a bucket
policy failed with *permission denied for table objects* before any policy was
consulted, so **a bucket wide open to the wrong reader looked exactly like one
locked down.** Fixed first; the other two findings were invisible until it was.

### 2.2 A withdrawn document was still downloadable — *severe*

Withdrawal removed the row from every read path and left the file reachable. The
bucket policy checked only that it sat in the reader's own folder, so anyone
holding the path — which the app had a moment earlier — could still fetch it with
a signed URL. **The central promise of the feature was only ever true of the
row.** The same check was already present for chat attachments and simply
missing here. Lab reports live in a second bucket, are the same documents, and
had the identical hole.

**The first fix leaked everything it was written to stop.** A storage policy that
inlines `NOT EXISTS (SELECT 1 FROM health_documents …)` evaluates that subquery
**under the reader's own row visibility** — and a withdrawn row is invisible to
them, so the check found nothing and passed. It goes through a `SECURITY
DEFINER` helper now. The delete rule worked from the first attempt only because
it already did.

### 2.3 A patient could hard-delete a clinician's document — *severe*

Row and file both. `useHealthDocuments` explains at length why archiving exists —
*"a document a clinician has already been given should not be able to vanish
from under them"* — and then exported a delete that did exactly that, permitted
by a policy with no condition beyond ownership. They could also delete the file
behind a **withdrawn** document, which is the evidence of a disclosure somebody
has to answer for.

## Pass 3 — the whole branch

Eight findings.

### Findings

*(3.1 to 3.3 are the pass 2 findings above, confirmed and closed in this pass.)*

### 3.4 Four delete policies predated the record rule

Each granted deletion on ownership alone. Reasonable when the tables were new;
wrong once other people relied on what was in them.

| Table | Was | Now |
|---|---|---|
| `clinician_guidance` | the author could delete advice the patient had acted on | only guidance never acknowledged |
| `medications` | a patient could delete a row imported from a hospital system, which the interface already refused | only their own entries, and only with no dose history |
| `schedule_entries` | a patient could delete a **missed** dose, rewriting the adherence a clinician reads | only doses not yet due |
| `clinician_patient_records` | a clinician could delete a record the patient had **claimed**, taking the onboarding attribution the institution is paid on | only unclaimed records |

### 3.5 The cascade that walked through 3.4 — *found by testing the neighbour*

`schedule_entries.medication_id` cascades. So a patient blocked from deleting a
missed dose could delete the **medication** and take the entire adherence
history with it. The protection held for one statement and not for the obvious
second one. Deleting is now only for a medication with no history; anything
taken is stopped instead, which keeps every dose.

### 3.6 Revoking a share erased the advice given through it — *severe*

`clinician_guidance.share_id` cascaded from `provider_shares`, and patients held
DELETE on their own shares. Ending access removed **every instruction the
clinician had issued through it**, acknowledged or not, from both sides, with no
trace.

Two things were wrong and both are fixed. Revocation here is deactivation —
`is_active`, `revoked_at`, `revoke_reason` all exist for it, a guard trigger
polices them, the patient is shown a sharing history built from them, and no
client code deletes a share; the DELETE policy was a leftover that did nothing
but make this reachable. And the cascade itself is now `SET NULL`, because a
policy is one route to a delete and the service role is another.

Same shape on `record_change_proposals.medication_id`: a **declined** proposal is
the record of a patient refusing a change, and it was going with the medication.

### 3.7 A guard that blocked the constraint's own repair

`enforce_guidance_patient_update()` stops a patient rewriting guidance by
restoring every clinical column from `OLD`, and `share_id` was in that list. So
when the new `SET NULL` fired — the constraint's own action, not an edit by
anyone — the trigger put the old value straight back and the delete then failed
on the constraint it was satisfying. `share_id` may now go to NULL and nowhere
else: a patient still cannot re-point guidance at a different share.

### 3.8 The constraint that then refused the row it was protecting

`proposal_names_its_target` required a change or stop to name a medication —
correct while open, wrong the moment the link was nulled because the medication
was removed. Scoped to what it was for: a proposal still **open** must name its
target; one already answered is history, and history may point at something that
no longer exists.

## Pass 4 — over-blocking, and the names in between

The three passes above were all restrictions. This one asks the opposite
question, because **a rule that also stops the legitimate case is a bug with
better manners** — and it presents as nothing happening, which is the hardest
kind to notice.

### 4.1 The ordinary day, asserted

`happy_paths.test.sql` is new and is not a security test. It is the list of
things a patient and a clinician actually do, each one there because something
in the last three passes could plausibly have broken it: upload, archive,
restore, delete an own document; read, edit, stop a medication; mark a dose
taken; record a reading; a clinician filing a document and the patient reading
it; issuing guidance and acknowledging it; proposing a change and accepting it;
withdrawing a document and the patient being told in plain words; revoking a
share and the clinician's access ending without anything being destroyed.

All of it still works. Nothing in the tightening over-reached.

The two failures it produced along the way were both the test being wrong, and
both worth recording because they confirm the design: a clinician upload
requires `source_context = 'clinician_upload'` at the row level (the client
sets it), and **a clinician cannot insert a medication at all** — they propose,
and the patient accepts.

### 4.2 Withdrawal across every share path

Verified rather than assumed: a withdrawn document leaves the per-document
share, the whole-vault share, the institution share and the owner's own view at
once. It does.

### 4.3 The other buckets

Swept every storage policy of the same owner-folder shape. The rest —
`clinician-dictations`, `voice-notes`, `medication-photos`, `patient-avatars`,
`simple-mode-images` — hold owner-created content rather than anything a
clinician sends, so there is nothing to withdraw and the shape is right there.

### 4.4 A whole class nothing was checking

Typecheck cannot see the database; the SQL suites cannot see `src/`. So a
misspelled RPC or a table renamed in a migration but not in a hook fails only at
runtime, for one user, on one screen. That gap is wide here because several new
tables are reached through untyped casts, which is exactly where a typo
survives.

`scripts/db-test.sh` now resolves every `rpc('…')` and `.from('…')` in `src/`
against the schema. Today all of them resolve. The check is deliberately
tolerant of one thing — `.from()` is both PostgREST and storage, so a name
passes if it is a public relation **or** a bucket; checking only the first
reported every bucket in the app as missing, which is how a useful check gets
switched off for crying wolf.

Verified by misspelling `stop_medication` and watching the runner name it.

## Checked and found sound

- Every table in `public` has RLS enabled. The six with no policies at all
  (`cron_auth`, `rate_limit_events`, `kingschat_login_attempts`,
  `beta_testers`, `beta_nda_signatures`, `contact_submissions`) are written only
  by edge functions under the service role — no client path reaches them.
- Trigger functions carry a default `EXECUTE` grant but are inert when called
  directly (*"trigger functions can only be called as triggers"*), so the RPC
  surface is not widened by them.
- Every `SECURITY DEFINER` function that writes and is callable by
  `authenticated` re-checks the caller: `withdraw_shared_file`,
  `object_to_withdrawal`, `respond_to_change_proposal`,
  `withdraw_change_proposal`, `stop_medication`. `apply_medication_proposal` is
  revoked from `authenticated` entirely.
- No client code deletes a `provider_share` or a `document_share`; revocation is
  deactivation throughout.

## Two things that are working as designed and cost an hour each

Recorded because the next person will hit them.

**`skip_duplicate_guidance()` silently drops guidance that repeats existing
guidance.** A fixture reusing wording from earlier in the same file vanishes with
no error, and the assertion then fails for a reason unconnected to its subject.
Worth knowing that a clinician re-sending identical advice also gets no
feedback.

**`SET LOCAL ROLE` and `set_config(…, true)` are transaction-scoped.** Long test
blocks carry state between sections, and an assertion can pass or fail on
whatever the previous one left behind. The cascade assertions were moved into
their own block with their own people for exactly this reason.

## Pass 5 — sign in and look at it

Four passes had established that the rules are right. None of them could say
what the rules look like from the other side of the screen, which is where a
correct refusal still reads as nothing happening and a correct row still gets
labelled with the wrong word.

### 5.0 The instrument, and why it is worth describing

The hosted Supabase project is not reachable from this session — the egress
policy refuses `cwngpcxxwvspcpkbxeax.supabase.co`, and the Docker daemon that
`supabase start` needs is not running either. So the browser was pointed at a
local stand-in: the real migration history replayed into a local Postgres, a
Supabase-compatible HTTP front end over it that opens a transaction per request
and `SET`s the caller's role and JWT claims, and the demo accounts seeded into
it. **Row policies are therefore enforced by the same Postgres that the suites
test**, through the same client code, in a real browser.

Two edge-function probes answer with a canned free tier because they run on
every screen; every other edge function answers with a visible refusal, so a
screen that silently depends on one shows up rather than hiding.

What this cannot cover: the edge functions themselves, the real storage service,
realtime, and anything about the hosted project's own configuration.

### 5.1 A clinician's reading, labelled as the patient's — *severe*

`EncounterScribePanel` and `FileDictationDialog` write a vital with
`source: "clinician"` when a clinician records a measurement during a visit.
That value was in none of the three places that decide what happens next:

- `VitalSource` did not include it, so nothing was type-checked against it;
- `VitalSourceBadge`'s lookup fell through to its default, which labels a
  reading **"You — recorded by you in OneCare"**;
- `isVitalEditable` refused it with **"Cannot edit vitals imported from EHR"**.

Seen in the browser, on the patient's own history: the doctor's 148/96 with an
Edit button, a Delete button, a confirmation reading *"This action cannot be
undone. The vital reading will be permanently removed from your history"* — and
then a toast blaming an EHR import that had never happened. `VitalHistoryLog`
rendered no provenance at all, so nothing on the row said who took the reading.

Fixed: `'clinician'` joins the union; the badge names it; the refusal names who
recorded it; and a row that is not the patient's shows the badge **instead of**
the controls, which is the rule the medicine cabinet already states in a comment
and the vitals surface never got.

### 5.2 The unit a reading was stored in — *severe*

`convertVitalValue(type, value, fromUnit?)` had an optional third parameter that
fell back to the config's unit. **All fifteen call sites omitted it**, so every
reading was declared already-canonical.

A glucose stored as 5.8 mmol/L — the unit an EHR import or a clinician dictation
writes — was shown to the patient as **"5.8 mg/dL"** and judged against a mg/dL
band, which paints a normal reading as a severe hypoglycaemia. `vital-stats.ts`
*did* pass the unit, so the statistics and the displayed reading disagreed with
each other; that disagreement is the tell, and it had been sitting in the file
since the stats were extracted.

Fixed by making `fromUnit` **required**, which is how all fifteen sites were
found — the compiler listed them. Verified in the browser: the card that read
"— mg/dL" now reads 97 mg/dL with a 108.1 average.

### 5.3 The alias map applied at display and not at selection

`VITAL_TYPE_ALIASES` exists because rows carry legacy and imported keys —
`blood_glucose`, `bp`, `spo2`, `pulse`. `getLatestVital` and `getVitalHistory`
compared `v.type === type` with no resolution, so such a row was listed in the
history log under its proper label **and simultaneously missing** from the card,
the chart and the statistics, which read "No readings" with the rows in the
table. Both selectors now resolve both sides.

### 5.4 An internal token printed at a patient

`medications.source` holds two different kinds of value. The EHR sync writes the
connection's provider name — "City General EHR" — which reads correctly in a
sentence. Everything else is an internal token. Four patient-facing strings
printed whichever they got, and the tooltip promised *"it will update on the
next sync"* to sources that never sync. One helper now decides, on the shape of
the value: a lowercase token with no spaces is ours to translate, anything with
a capital or a space is already a name.

### 5.5 A status nobody recognises, presented as consent

The clinician's record header rendered both badges by underscore replacement, so
`clinician_managed` arrived on screen as "clinician managed", and
`invitation_status` printed "accepted" directly beside the invite button's own
"Accepted" badge — twice for one fact.

The invite button was the more serious half: **"Invited" for exactly `invited`,
"Accepted" for everything else**, over a plain-text column with no `CHECK`
behind it. Any value an import or a later migration put there would have been
shown to a clinician as consent the patient had given.

Both columns now accept only the words the application knows, enforced by the
database, and both are labelled from one place.

**And then the neighbour.** Fixing the detail page left the patients *list* and
the status *filter dropdown* still rendering `invitation_status` by underscore
replacement — the same shape as half the findings on this branch, committed by
me, one commit earlier. Found by sweeping every `.replace(/_/…)` in `src/`
afterwards rather than by trusting the fix. The tests now assert the helper is
used at all four sites and that its vocabulary matches the migration's, so the
two cannot drift apart again.

`import-patient-records` took `data_sharing_model` straight from the request
body and never checked it, and a hundred lines down branched on it: anything
that was not exactly `clinician_managed` created a provider share under a model
nobody could name. It now names the word it will not accept.

### 5.6 Two small ones

Icon-only Edit and Delete buttons in the vitals history had no accessible name,
so a screen reader announced "button". And a `Badge` inside a `<p>` on the
clinician reports page is invalid nesting that React warns about on every
render.

### 5.7 The gap the pass did not close

**Nothing in the client reaches the withdrawal mechanism.** `withdraw_shared_file`,
`object_to_withdrawal`, `my_withdrawn_documents`, `practice_withdrawal_register`
and `document_retraction_events` are unreferenced in `src/` and in the edge
functions alike. Driven through the RPC directly, withdrawal behaves exactly as
designed: the document leaves the patient's Vault, the counter drops, their own
documents are untouched. But **the patient is told nothing** — a document they
could open yesterday is simply absent today — and a clinician has no way to
withdraw anything from inside the product at all.

The database half is finished and tested. The surface is not built. That is the
withdrawal portal still outstanding, and this is the concrete argument for it.

### 5.8 An instruction that falls out of every bucket

Found the same way as 5.5 and worth more: a fixture seeded a guidance row with
`status = 'active'`, a word the application never writes. The patient's
Instructions page sorts guidance into three exact-match buckets — `pending`,
`acknowledged`, `completed` — plus the archived one, so the row belonged to
none. The clinician's instruction was in the table, the clinician's screen
showed it as sent, and **the patient's page read "All caught up!"** with nothing
anywhere reporting a problem.

The fixture was wrong. Nothing in the database stopped a real write from being
wrong the same way: `clinician_guidance.status` was plain text with a default
and no `CHECK`. `schedule_entries.status` has the identical shape one step
further on — a dose matching no status is absent from the day and is counted
into neither `taken` nor `due`, so it moves the adherence figure the clinician's
risk view reads.

Both now hold only their screens' vocabulary, enforced by the database, and an
unrecognised value normalises to `pending` — the state that loses nothing: an
instruction the patient has not seen stays in front of them, and a dose of
unknown outcome is still owed. The unit tests read the vocabularies out of
`GuidanceStatus` and `ScheduleStatus` and assert the migration contains each
word, so the two cannot drift.

A survey of every `text` status column at the same time: ten of the newer tables
already carry a `CHECK` — that pattern is the branch's — and the remainder
(`beta_bug_reports`, `job_applications`, `qhin_imports`, `ehr_export_queue`,
`ehr_sync_logs`, `practice_members`, and three `*_invitations`) are recorded
here as a follow-up rather than changed blind. None of them buckets clinical
content on the patient's screen.

### 5.9 Two findings that were the instrument's fault, and what that cost

Worth recording because both were convincing.

**A twenty-digit average on the patient's dashboard.** `node-postgres` returns
`numeric` as a string to preserve precision; PostgREST renders it as a JSON
number. The strings reached `values.reduce((a, b) => a + b, 0)` and
concatenated. A real bug in the shim, no bug in the app.

**Schedule entries duplicating on every page load.** The shim compared
`timestamptz` filters as text, and `'2026-09-09 08:00:00+00'` sorts below
`'2026-09-09T00:00:00Z'` because a space precedes `T`. Every ranged query came
back empty, so the generator's "does this day already have entries?" check
always said no and always inserted. Sixteen rows for four doses, reproducible on
demand, and a plausible story about a read-then-write race between concurrent
callers. A migration adding a unique index was drafted before the harness was
checked. **Nothing about the application was wrong.**

The rule that saved both: when a finding depends on the instrument, test the
instrument first. The second one also invalidated two whole route sweeps — every
`gte`/`lte` filter in the app had been returning nothing — so both sweeps were
re-run after the fix, and both came back clean.

## Pass 6 — the final audit: reading every write policy against its neighbour

The previous five passes established that the *rules* are right and that the
*screens* built on them behave. This pass went back to the enumeration method
from passes 1–3 — every `pg_policies` row on the tables this branch touched,
read in full rather than sampled — because "the rule is right" had only been
checked for DELETE on `medications` and never checked for UPDATE, and never
checked for `vitals` at all.

### 6.1 A patient could rewrite or erase a clinician's own reading — *severe*

`isVitalEditable()` and `isMedicationEditable()` are the rule this whole branch
states: a row someone else recorded is their record, not the patient's to
change. Pass 5 taught every vitals screen to honour it — the Clinician badge
replacing Edit/Delete, the refusal naming who recorded it. All of that is UI.
Tested directly against RLS, signed in as the patient:

```sql
UPDATE public.vitals SET value = 90 WHERE id = <the clinician's reading>;
-- 1 row changed.
DELETE FROM public.vitals WHERE id = <the clinician's reading>;
-- 1 row removed.
UPDATE public.medications SET dosage = '50 mg' WHERE id = <the EHR-sourced row>;
-- 1 row changed.
```

`vitals` had no `source` check on UPDATE or DELETE at all — clinicians only
ever INSERT for a patient, so there was no legitimate write this narrows.
`medications` DELETE carried the guard (pass 3, 20260926100000); UPDATE never
did, which is the gap `guardImported()`'s own comment names without knowing
it: *"the same rule vitals have had all along"* — a rule neither table's
database had actually enforced.

Worse for vitals: the assistant's `delete_vital` action never selected
`source` at all, so telling the assistant "delete my last blood pressure
reading" could delete the clinician's own reading with no refusal — reachable
from the chat, not only from a raw API call. Fixed to mirror
`refuseIfNotTheirs`, naming who recorded the reading rather than silently
declining or silently succeeding.

Both RLS policies now carry the same `source IS NULL OR source = 'manual'`
guard the medications DELETE policy already had, applied consistently to both
tables and both verbs. The proposal-acceptance and `stop_medication` paths are
unaffected — both run `SECURITY DEFINER` and never touch this policy, verified
by re-running `stop_medication.test.sql` and `change_proposals.test.sql`
against the tightened policy rather than assumed.

**Confirmed live in the browser, not only at the SQL level:** the shim was
brought back up, the migration applied, and the patient's own History tab was
driven through Playwright — the clinician's 148/96 reading renders with a
Clinician badge and no Edit or Delete button, exactly as the fix intends.

### 6.2 A pre-existing test asserted the bug as a feature

`dictation_filing.test.sql` had "the patient can still add their own readings
and remove one recorded for them" — literally a clinician-recorded reading —
framed in its own comment as *"the patient stays in charge of their own
record."* That was written before this branch's provenance rule existed, and
it is the exact asymmetry that rule now closes: a clinician cannot rewrite or
erase the patient's chart, and — as of this pass — the reverse holds too.
Updated to assert the corrected behaviour rather than weakened to fit it,
following the same principle `deletion_rules.test.sql`'s `'pending'` fixture
followed in pass 4: when a fixture encodes the bug, the fixture is what
changes.

### 6.3 Checked and found sound

Read in the same sweep and not changed, with the reasoning that closed each
one:

- **`health_documents` UPDATE has no `source`-style guard** — a patient can
  retitle, re-tag, re-categorise, add notes to, or set the `document_date` on
  a clinician-filed document. Different in kind from a vitals value or a
  medication dosage: this is the patient's own filing metadata, the
  underlying file is never touched through this path, and DELETE already
  refuses outright for anything `uploaded_by_user_id` marks as not theirs.
  Not the same finding as 6.1; recorded rather than silently passed over.
- **`clinician_guidance`'s patient UPDATE policy has no `WITH CHECK` narrowing
  columns** — RLS cannot restrict columns, only rows. A
  `BEFORE UPDATE` trigger (`enforce_guidance_patient_update`, built in pass 3)
  does the column-level work instead, reverting every field but `status`,
  `acknowledged_at` and `completed_at` to `OLD`. Tested directly: a patient's
  attempt to rewrite `instruction`, `title` and `priority` through the
  status-update policy left all three unchanged; the legitimate acknowledgement
  write still landed. Sound.
- **`provider_shares`' patient UPDATE has no column restriction either** — by
  design, confirmed by reading `guard_provider_share_consent()`: the row is
  the patient's own consent decision, so widening or narrowing it is theirs to
  do. Only the clinician side of the relationship is blocked from touching the
  terms. Correctly scoped, not the same shape as 6.1.
- **`record_change_proposals` has no UPDATE or DELETE grant to `authenticated`
  at all** — accept/decline goes only through `respond_to_change_proposal()`.
  No raw-write surface exists to check.
- **Storage bucket policies** — all 43, spot-checked against the pass-2 and
  pass-4 fixes; both are still in place, unaffected by this session's changes.

### 6.4 New tests

`supabase/tests/record_provenance_write_guard.test.sql` — dedicated coverage
for 6.1: the clinician's reading survives an UPDATE and a DELETE attempt
unchanged, the patient's own manual entry is untouched by the guard, an
EHR-sourced medication's dosage cannot be silently rewritten, and
`stop_medication()` still works on that same row afterward. Verified by
reverting the migration and watching it fail before restoring it.

`src/test/assistant-actions-gate.test.ts` gained a fourth `describe` block,
matching the existing medications one exactly: the `delete_vital` branch
selects `source`, refuses by name using the same `isVitalEditable` /
`describeVitalSource` the vitals screens use rather than a private copy, and
the refusal test was confirmed to fail when the guard is removed.

## Pass 7 — asked directly whether it was safe to assume no bugs remained

The honest answer to that question is no, and cannot be yes: six passes in a
row, each believed thorough, each found something real. There is no method
that proves absence, only a method that has not yet found presence. What this
pass could do was attack from an angle none of the first six had used.

Passes 1–6 all asked, in one form or another, *can the patient rewrite or
erase what a clinician recorded* — UPDATE and DELETE. None of them asked the
mirror question: *can the patient write a row that claims to be the
clinician's in the first place* — INSERT. That gap held three findings, one
per table pass 6 had just finished protecting the read side of.

### 7.1 A patient could forge a clinician's own reading — *severe*

Both `vitals` and `medications` INSERT policies checked only
`auth.uid() = user_id` — nothing else. Signed in as a patient with no share to
any clinician at all:

```sql
INSERT INTO public.vitals (user_id, type, value, unit, source, recorded_by_user_id)
VALUES (me, 'blood_pressure', 118, 'mmHg', 'clinician', <any UUID>);
-- 1 row inserted, no relationship required.

INSERT INTO public.medications (user_id, name, dosage, frequency, source, external_id)
VALUES (me, 'Oxycodone', '30 mg', 'as_needed', 'City General Hospital', 'RX-FORGED-001');
-- 1 row inserted, no connection required.
```

This is the more serious mirror of 6.1, for two reasons. First, it is the
scenario this branch's design conversation named early on — a patient making
a change and having it appear to come from the doctor — realised on the
*origin* of a row rather than an edit to one, and realised on vitals as well
as medications. Second, and specifically *because* of 20260929100000: a
forged row is now more durable than before that fix, not less. The very
policy built to stop a patient from touching a real clinician's reading now
also protects a fabricated one wearing its badge — the patient who forged it
can no longer be the one to take it back.

Fixed with the same shape as 6.1: the patient's own INSERT policy now carries
`source IS NULL OR source = 'manual'`, plus a restriction on the columns that
name a specific origin — `recorded_by_user_id` (null, or the patient
themselves — recording one's own reading and saying so is not a claim about
anyone else), `external_id`, `ehr_connection_id`. Every legitimate
patient-facing write path was read before writing the fix, not assumed:
`useVitals.ts`'s `addVital`, the assistant's `log_vital` and `add_medication`,
and `AddMedication.tsx` all either write `source: 'manual'` explicitly or
write nothing and take the column default; none of them ever sets the columns
now restricted. The separate, correctly-scoped clinician INSERT policy on
vitals is untouched, and RLS policies on the same command are OR'd, so a real
clinician's insert still succeeds regardless of what the patient's own policy
allows. The EHR sync and CSV import edge functions run as `service_role`,
which bypasses RLS, so neither is affected either.

Confirmed against the real HTTP path, not only direct SQL: the identical
insert `AddMedication.tsx` performs, missing only the `user_id` the hook adds
automatically, was rejected by the shim exactly as intended — then succeeded
once `user_id` was included, matching what the real app actually sends.

### 7.2 The same gap, a third table

Reading every INSERT policy on every table with more than one — the shape
this bug leaves — turned up `health_documents`. `"Users can upload their own
documents"` also checked only `auth.uid() = user_id`:

```sql
INSERT INTO public.health_documents
  (user_id, file_path, file_name, title, uploaded_by_user_id, source_context)
VALUES (me, ..., 'Fit to work certificate', <any clinician's uuid>, 'clinician_upload');
-- 1 row inserted.
```

`source_context = 'clinician_upload'` is the exact string `DocumentCard.tsx`
checks to render **"From your clinician."** `uploaded_by_user_id` is the exact
column the pass-3 DELETE policy requires to be null before a patient can
remove a document themselves. The same fabricated certificate that displays
with a clinician's badge is also, the moment it lands, outside the patient's
own ability to take back — a fitness-for-work letter, a fabricated referral,
anything with real consequence attached to a clinician's name.

Unlike vitals and medications, `source_context` is a genuine multi-valued tag
with several legitimate patient-side values — read from every caller of
`uploadDocument()` before writing this fix, not assumed: `direct`,
`vitals_upload`, `assistant`, `patient_recording`, `care_record_snapshot`
(via `CARE_RECORD_SOURCE`), `invoice`, `message_attachment`. The fix is a
denylist on the one reserved value plus the null requirement on
`uploaded_by_user_id`, not an allowlist that would have broken the other six.

### 7.3 Checked and found sound

The same enumeration — every table with more than one INSERT policy, the
signature shape of this bug class — read in full rather than sampled:

- **`messages`** — both policies require `auth.uid() = sender_user_id`
  directly; a patient cannot claim to be the sender of a clinician's message
  because the row's own sender column is pinned to whoever is actually
  inserting. Sound.
- **`qhin_imports`** — both policies require `auth.uid() = requested_by`
  directly, same shape. Sound.
- **`enterprise_inquiries`** — a B2B sales inquiry, not a clinical record;
  `clinician_user_id` is either null (anonymous) or pinned to the inserter.
  Not the same bug class.
- **`data_sharing_agreements`** — `agreed_by` looks like the same shape
  (`text`, unrestricted) but is write-only: grepped across `src/` and
  `supabase/`, nothing ever reads it to make a trust decision or render a
  claim to a third party. The one client write hardcodes `'patient'`
  regardless of what a raw call could set. Recorded rather than silently
  passed over, because it looked like the bug at first read and the
  difference — read versus write-only — is worth stating, not assuming.
- **`clinician_patient_records`** — both INSERT policies require
  `auth.uid() = clinician_user_id`; a clinician cannot claim to be a
  different clinician, and patients do not insert into this table at all
  (only UPDATE, already covered in pass 6). Sound.

### 7.4 New tests

`supabase/tests/provenance_forgery.test.sql` — the mirror of
`record_provenance_write_guard.test.sql`: a patient cannot forge clinician
provenance on a fresh insert, on any of the three tables, with or without a
real share to the clinician being impersonated; every legitimate value on
every table still succeeds, including the plain no-`source`-given path; the
real clinician's own insert, through their own separate policy, is
unaffected. Confirmed to fail before each half of the fix and pass after,
for both halves independently.
